# Providers

Providers teach XFTY how to generate test data for a particular `SObject` type.

Every supported object has exactly one Provider responsible for describing:

- how the object is created
- which default values it receives
- which relationships it has
- how those relationships should be generated

Providers are intentionally declarative. They describe *what* valid test data looks like rather than imperatively constructing records.

---

# The Role of a Provider

Suppose a test requests a `Contact`.

```apex
Contact contact = (Contact) new XFTY_DummySObjectProvider(Contact.SObjectType, providerLookup)
    .supply();
```

The `XFTY_DummySObjectProvider` itself contains no knowledge of Contacts.

Instead, it asks the configured Provider Lookup for the Provider responsible for `Contact`.

The Provider then constructs a Master Template describing how Contacts should be generated.

---

# Provider Architecture

The generation process looks like this:

```text
Test
 │
 ▼
XFTY_DummySObjectProvider
 │
 ▼
Provider Lookup
 │
 ▼
Contact Provider
 │
 ▼
Master Template
 │
 ▼
Bundle
```

Each component has a single responsibility.

| Component | Responsibility |
|-----------|----------------|
| `XFTY_DummySObjectProvider` | Public API used by tests |
| Provider Lookup | Finds the correct Provider |
| Provider | Defines default data |
| Master Template | Stores generation rules |
| Bundle | Stores generated object graph |

Keeping these responsibilities separate makes Providers easy to understand and extend.

---

# Implementing a Provider

A Provider implements `XFTY_DummySobjectProviderIntf`.

```apex
@IsTest
public class DefaultContactDataProvider implements XFTY_DummySobjectProviderIntf {
    public static final String DEFAULT_FIRST_NAME_PREFIX = 'Contact First Name';
    public static final String DEFAULT_LAST_NAME_PREFIX = 'Contact Last Name';
    public static final String DEFAULT_EMAIL_PREFIX = 'test.contact';
    public static final String DEFAULT_ACCOUNT_DESCRIPTION = 'Account for contact';

    private static final SObjectField PRIMARY_TARGET_FIELD = Contact.Id;
    
    private static final XFTY_DummySObjectMasterTemplate MASTER_TEMPLATE = new XFTY_DummySObjectMasterTemplate(PRIMARY_TARGET_FIELD)
            .put(Contact.AccountId, new XFTY_DummyDefaultRelationshipRequired(new Account(
                    Description = DEFAULT_ACCOUNT_DESCRIPTION
            )))
            .put(Contact.Email, new XFTY_DummyDefaultValueUniqueEmail(DEFAULT_EMAIL_PREFIX))
            .put(Contact.FirstName, new XFTY_DummyDefaultValueIncrementingString(DEFAULT_FIRST_NAME_PREFIX))
            .put(Contact.LastName, new XFTY_DummyDefaultValueIncrementingString(DEFAULT_LAST_NAME_PREFIX));

    public SObjectField getPrimaryTargetField() {
        return PRIMARY_TARGET_FIELD;
    }

    public XFTY_DummySObjectMasterTemplate getMasterTemplate() {
        return MASTER_TEMPLATE;
    }

    public XFTY_DummySObjectBundle createBundle(
            XFTY_DummySObjectProviderLookupIntf providerLookup,
            List<SObject> templateSObjectList,
            XFTY_InsertModeEnum insertMode,
            XFTY_InsertInclusivityEnum inclusivity
    ) {
        return XFTY_DummySObjectFactory.createBundle(providerLookup, MASTER_TEMPLATE, templateSObjectList, insertMode, inclusivity);
    }
}
```

Most Providers follow exactly this pattern.

---

# Primary Target Field

Every Provider declares a Primary Target Field. This field identifies the primary objects generated by the Provider when they are stored in a `Bundle`.

For most `SObject`s this is simply the `Id` field:

```
Contact.Id
```

However, not every Salesforce object can be treated this way. Some object types either do not expose a traditional `Id` field or require relationships to be established through another field.

By allowing each Provider to specify its own Primary Target Field, XFTY remains independent of those implementation details while giving advanced Providers the flexibility to define alternative identity strategies when necessary.

Most Providers should simply return `MyObject.Id`.

---

# Master Templates

Providers construct a Master Template describing the default data for an object.

A Master Template contains:

- default field values
- required relationships
- optional relationships

For example:

```apex
new XFTY_DummySObjectMasterTemplate(Contact.Id)
    .put(Contact.FirstName, new XFTY_DummyDefaultValueIncrementingString( 'Contact'))
    .put(Contact.Email, new XFTY_DummyDefaultValueUniqueEmail('test.contact'))
    .put(Contact.AccountId, new XFTY_DummyDefaultRelationshipRequired(new Account()));
```

Think of a Master Template as the canonical definition of a valid object.

Every generated record begins here.

---

# Keep Master Templates Declarative

Master Templates should describe data, not algorithms.

Good:

```apex
.put(Contact.FirstName, new XFTY_DummyDefaultValueIncrementingString('Contact'))
```

Avoid imperative logic that manually constructs records.

Keeping Providers declarative makes them easier to understand, easier to maintain, and far easier to update when validation rules change.

---

# Discovering Required Fields

Creating a new Provider is usually an iterative process.

Start by adding the fields required by the Salesforce platform itself.

These include:

- required fields
- Master-Detail relationships
- mandatory lookup relationships

Many IDEs expose this information directly from Salesforce metadata.

For example, if you're using **Illuminated Cloud** with IntelliJ IDEA:

1. Open the generated Apex definition for the `SObject`.
2. Search for **Master Detail** relationships.
3. Search for `Required: true`.

These hints are an excellent starting point.

However, they are not exhaustive.

Many organizations introduce additional requirements through:

- Validation Rules
- Flows
- Apex Triggers
- Duplicate Rules
- Workflow Rules
- custom business logic

The simplest approach is usually to attempt an insert, identify the missing requirement, update the Master Template, and repeat until records are valid.

Resist the temptation to make every relationship required.

Only include fields and relationships that are genuinely necessary for valid test data.

Keeping Master Templates minimal produces smaller object graphs and faster tests.

---

# Relationship Design

Relationships deserve special consideration.

Ask for every relationship: Can this object reasonably exist without the related record?

If the answer is **no**, use

```apex
XFTY_DummyDefaultRelationshipRequired
```

If the answer is **yes**, use

```apex
XFTY_DummyDefaultRelationshipOptional
```

This distinction has a significant impact on test performance.

# Provider Lookups

Providers are discovered through an implementation of

```apex
XFTY_DummySObjectProviderLookupIntf
```

A typical implementation simply maps each supported `SObjectType` to its Provider.

```text
Account
    ▼
Account Provider

Contact
    ▼
Contact Provider

Opportunity
    ▼
Opportunity Provider
```

Separating lookup from generation allows different projects to provide different implementations without modifying XFTY itself.

---

# Multiple Provider Configurations

A Provider Lookup is more than a registry—it also acts as a compilation boundary.

In many Salesforce projects, different SObject types are defined in different unlocked or managed packages.

Referencing an `SObject` that is unavailable in the current package causes compilation failures, even if that Provider would never actually be used.

By allowing applications to provide different Provider Lookup implementations, each package can register only the Providers that are valid within its compilation context.

This allows XFTY to be shared across packages without introducing unwanted compile-time dependencies.

# Record Types

XFTY currently keys Providers exclusively by `SObjectType`.

This means a single Provider is responsible for all Record Types belonging to a particular object.

For many objects this is sufficient.

However, some objects have Record Types that differ so significantly that they effectively behave like different entities.

A common example is Business Accounts versus Person Accounts.

In these situations, Providers typically select the appropriate Master Template themselves based on information contained in the supplied Override Template.

For example:

```apex
	public XFTY_DummySObjectBundle createBundle(
			XFTY_DummySObjectProviderLookupIntf providerLookup,
			List<SObject> templateSObjectList,
			XFTY_InsertModeEnum insertMode,
			XFTY_InsertInclusivityEnum inclusivity
	) {

		// This is a bit hacky, but it allows us to control which template to use when creating a bundle.
		// We can use a different SObject field to control this, but the same master needs to be used for each
		// record at the top level of the bundle.
		// (Control at a deeper level has not been investigated, but it may be necessary to use a differed XFTY_DummySObjectFactoryOutletLookupIntf.)
		Id requiredRecordTypeId = (Id) templateSObjectList[0].get(Account.RecordTypeId);
		XFTY_DummySObjectMasterTemplate masterTemplate = (requiredRecordTypeId == PERSON_RECORD_TYPE_ID)
                      ? PERSON_TEMPLATE 
                      : MASTER_TEMPLATE;

		if (masterTemplate == null) {
			throw new XFTY_DummySObjectFtyProviderException('Unsupported Account Record Type: ');
		}

		return XFTY_DummySObjectFactory.createBundle(providerLookup, masterTemplate, templateSObjectList, insertMode, inclusivity);
	}
```

The Provider can then select an appropriate Master Template before delegating to the factory.

This approach works, although it does require Provider-specific logic and means that every record generated at the top level of a single Bundle shares the same Master Template.

Future versions of XFTY may support richer lookup keys (for example `SObjectType + RecordType + Flavor`), but the additional complexity has so far outweighed the practical benefits.

# Platform Events

Platform Events differ from ordinary `SObject`s.

They cannot be queried using SOQL after publication and have different lifecycle rules.

Although XFTY can generate Platform Event instances like any other object, Providers should avoid assumptions based on record persistence.

---

# QueueSObject

`QueueSObject` behaves differently from most relationship objects.

If your application depends on Queue membership, verify the generated data behaves as expected before relying on default relationship generation.

---

# Testing Providers

Whenever a new Provider is created, it should have its own test class.

Provider tests should verify:

- records can be generated
- required relationships are populated
- insertion succeeds (when appropriate)
- optional relationships behave correctly
- unique values remain unique

A failing Provider test is usually much easier to diagnose than dozens of unrelated application tests failing because a validation rule changed.

---

# Best Practices

- Keep Providers small.
- Keep Master Templates declarative.
- Include only genuinely required fields.
- Prefer optional relationships whenever possible.
- Avoid conditional logic.
- Test each Provider independently.
- Create alternative Provider Lookups rather than complex Providers.

---

# Design Philosophy

Providers deliberately separate *what* test data looks like from *how* it is generated.

Tests describe only the values they care about.

Providers describe valid defaults.

The framework combines the two to produce complete, valid test data while keeping tests concise and resilient to future changes.

This separation is the primary design goal of XFTY and is what allows validation rules, required fields, and relationship changes to be maintained in a single location rather than duplicated throughout an entire test suite.
